# Content Strategy

## Purpose

This document defines what content belongs in Matthew Blanke's portfolio, how much of it should be visible, and how information should be prioritized.

The previous portfolio direction became too wordy.

This document exists to prevent that from happening again.

The central content principle is:

> **Show first. Explain second.**

The portfolio should communicate through:

- composition
- objects
- motion
- hierarchy
- concise labels
- selective detail

before it relies on paragraphs.

---

# Core Rule

A major scene should generally expose no more than approximately **40–60 visible words by default**.

Many scenes should use substantially less.

The visitor should never encounter a wall of text that feels intimidating to read.

If a scene requires several paragraphs to explain itself, the content architecture or visual storytelling is probably not strong enough.

---

# Content Layers

All content should be classified into one of three layers.

## Layer 1 — Primary

Immediately visible.

This is the minimum information required to understand the scene.

Examples:

- project name
- one-line explanation
- role/company
- school/field
- live link
- contact action

## Layer 2 — Supporting

Short supporting context.

Examples:

- technology line
- dates
- status
- role
- one technical note
- selected coursework
- one concise result

Layer 2 should remain visually subordinate.

## Layer 3 — Deep Detail

Optional.

Examples:

- architecture
- database decisions
- development history
- project evidence
- full résumé bullets
- detailed technical context
- extended academic explanation

Deep detail should never be forced into the main scroll journey.

---

# Writing Style

Copy should be:

- concise
- specific
- plainspoken
- confident
- factual
- natural
- easy to scan

Avoid:

- startup-founder voice
- LinkedIn voice
- design-agency jargon
- academic over-explanation
- résumé duplication
- self-congratulation
- vague adjectives

Especially avoid phrases like:

- passionate about
- lifelong learner
- problem solver
- crafting experiences
- at the intersection of
- where technology meets
- obsessed with
- innovative solutions
- cutting-edge
- results-driven
- detail-oriented

unless they are literal sourced language that truly needs to appear.

Specific facts are better than flattering adjectives.

- one concise signal

## Supporting Detail

Potentially one concrete result or responsibility.

Example:

```text
Grocery section lead.
```

or:

```text
Physics + math tutoring.
```

Leave for résumé.

## Avoid

- five bullets per role
- full job descriptions
- generic lessons
- forced software analogies
- motivational framing

Do not write:

> Trader Joe's taught me the importance of teamwork.

If there is a meaningful concrete fact, show that instead.

# Résumé Content Boundary

The résumé exists specifically so the main site does not need to contain everything.

The résumé should own:

- complete education
- detailed experience bullets
- technical skills
- awards
- certificates
- full project detail where appropriate

The portfolio should summarize and visualize.

A useful test:

> If this information is mainly useful for formal evaluation rather than storytelling, it probably belongs in the résumé.

---

# Technical Stack Content

Technology should be shown selectively.

Do not create logo soup.

Prefer concise text:

```text
NEXT.JS / SUPABASE
```

or:

```text
SWIFTUI / FASTAPI
```

Only list technologies that materially help explain the project.

Do not list every library.

---

# Metrics and Evidence

Only show metrics when they are:

- meaningful
- verified
- understandable
- impressive or explanatory

Do not show counts merely because they exist.

Bad examples:

- number of migrations
- number of test files
- number of commits
- number of CI jobs

unless those counts genuinely communicate something important.

Better examples might include:

- live users
- measurable growth
- performance improvement
- reliability improvement
- concrete adoption

Only publish verified metrics.

---

# Project Authorship

Be precise.

For each project, distinguish:

- solo
- team
- course project
- post-course continuation
- specific role

Do not imply sole authorship when unsupported.

Do not bury team context simply to make a project sound stronger.

The portfolio should remain credible.

# Content Source of Truth

All content is stored in source control.

Likely organization:

```text
content/
  projects.ts
  experience.ts
  education.ts
  personal.ts
```

Content should be structured enough that:

- visible copy
- metadata
- links
- alternate labels

can be managed cleanly.

There is no CMS.

# Content Verification

Before publication, every factual claim should be verified.

Examples:

- dates
- project status
- stack
- role
- team/solo attribution
- academic facts
- employment facts
- metrics
- links

Do not rely on memory if a claim can be verified from:

- source repositories
- résumé
- transcripts
- official course records
- project files
- live product pages

---

# Personal Content and Privacy

Only publish personal information intentionally selected for the portfolio.

Do not expose:

- precise address
- phone number
- private email addresses
- private account identifiers
- employee IDs
- private school-system information
- private schedules
- private messages
- private documents
- other people's personal data

A fact existing in a local file does not mean it belongs on the public site.

# Content Rhythm

Text density should change with scene intensity.

## Hero

Very little text.

## Flagship Project

Short explanation + metadata.

## Experience

Short role lines.

## Education

Mostly labels and clusters.

## Off the Clock

Mostly labels.

## Contact

Almost no explanatory prose.

This creates a progressively visual experience rather than a text-heavy one.

# Copy Review Checklist

Before approving any visible copy, ask:

### Is this necessary?

If not, remove it.

### Can the visual explain it?

If yes, reduce the copy.

### Is this duplicated elsewhere?

If yes, choose one location.

### Is it specific?

Replace vague adjectives with concrete facts.

### Is it easy to scan?

Shorten where possible.

### Does it sound like LinkedIn?

Rewrite.

### Does it sound like a design agency?

Rewrite.

### Is it trying too hard to sound profound?

Simplify.

### Does it belong in the résumé instead?

Move it.

### Is it verified?

If not, hold it.

# Final Content Standard

The portfolio should never feel like:

> a résumé rewritten into web sections.

It should feel like:

> **a visual experience where every visible word has earned its place.**

When choosing between:

- another paragraph
- a stronger composition

prefer the stronger composition.

When choosing between:

- more metadata
- clearer hierarchy

prefer clearer hierarchy.

When choosing between:

- proving everything
- making the important thing obvious

make the important thing obvious.
